## 5. 已裁决并落地（D-04 · 方案 B）

### 5.1 现象

## 10. 2026-10-28 收口记录

### 10.1 D-07 结算退款冲抵（按技术架构 3.10.2 / 3.10.4 实现）

**修复前**：`refundAmount`、`carryForwardAmount` 由 `bill.setRefundAmount(0L)` / `setCarryForwardAmount(0L)` 硬编码；已结算订单退款后系统不做任何回收，商家「既收了钱又退了款」，正是规格书 8.8 要防的资金穿底。

**修复后计算口径**：

```text
orderPayable    = Σ( gross − merchant_discount + platform_discount − commission )   // 本期可入账订单
refundAmount    = Σ( 已结算订单的「原应结金额」)                                      // 本期冲抵
carryForwardIn  = 上期 carry_forward_amount（仅一次）
payable         = orderPayable − refundAmount + carryForwardIn
若 payable < 0  → carry_forward_amount = payable，payable 置 0（本期不扣款，转下期负项）
```

**三个关键设计决策**：

| 决策 | 选择 | 理由 |
|---|---|---|
| 冲抵基数 | 该订单**原应结金额**（账单内 `item_type=1 + 2` 之和），而非用户退款额 | 用户退款额含配送费（归平台）且受平台券影响；按它冲抵会让商家替平台承担 500 分；按原应结冲抵可保证「全额退款后商家该单净额为 0」 |
| 幂等 | `item_type=4 + source_id=退款单ID` 唯一；承接用 `item_type=5 + source_id=上期账单ID` | 账单生成后不可修改，无法回写上期账单表示「已承接」，只能靠明细存在性判定 |
| 入账口径 | 未结算即退款的订单不冲抵（仍被 `refund_status=0` 过滤，天然不入账） | 只有「已结算拿过钱」才需要回收，避免重复扣减 |

**资金恒等式验证**：`SettlementRefundOffsetTest#billAmountsSatisfyFormula` 断言
`payableAmount == grossAmount − merchantDiscount + platformDiscount − commissionAmount − performanceFee − refundAmount + carryForwardAmount`，任何一侧失衡即红灯。

### 10.2 规格书 8.4 账单公式裁定

**冲突事实**：规格书 8.4 文字写「营业额 − 平台抽佣 − **平台承担优惠** + **商家承担优惠** + 退款冲抵」；技术架构 3.10.2 公式为：

```text
payable = gross − merchant_discount + platform_discount − commission − performance_fee − refund_amount
```

两者符号**完全相反**。区别在于：平台承担优惠是平台掏钱补贴用户，商家不应为此少拿钱（应 **+**）；商家承担优惠是商家自己让利（应 **−**）。若按 8.4 文字实现，会造成「平台做活动、商家赔钱；商家自己做活动、反而多拿钱」的错账。

**甲方裁定（2026-10-28）**：**以公式为准，忽略矛盾的文字描述。**

**代码现状核对**：`SettlementServiceImpl` 原实现 `merchantAmount = gross − merchantDiscount + platformDiscount − commission` **已符合公式**，本轮未改动符号，仅补齐 `refundAmount` 与 `carryForward` 两个缺失项。

**待办（文档侧，非代码）**：建议修订 `docs/外卖需求规格说明书.md` 第 1329 行与 4.8 节「结算明细」处的文字表述，与 3.10.2 公式对齐。本报告不改甲方文档，仅记录裁定。
