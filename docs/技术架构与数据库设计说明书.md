### 0.3 术语与状态码

| 术语 | 含义 |
|---|---|
| 订单 | 用户下单形成的交易单据，含配送单与自取单两种履约方式 |
| 配送单 | 骑手侧履约单据，一份订单最多一条 |
| 支付单 | 一次支付请求，一个订单可有多条支付单 |
| 退款单 | 一次退款请求，一个订单可有多条退款单 |
| 可结算时间 | `completed_at + after_sales_days`，到达后才进入账单 |
| 幂等键 | 客户端 `Idempotency-Key` 或服务端业务唯一键 |
| Outbox | 与业务同事务落库、事务后异步投递的消息表 |

状态码统一使用 `tinyint`，取值见第 3 章和 2.x 建表注释。金额统一使用 `bigint` 分，费率使用 `decimal(6,4)`。

### 0.4 P0 范围与简化

| 项 | P0 | P1/P2 |
|---|---|---|
| 支付 | 支付宝沙箱、余额、模拟微信，单通道 | 组合支付、对账、退款重试 |
| 结算 | 技术服务费 + T+1 账单 + 模拟打款 | 履约服务费、活动加佣、商家等级费率 |
| 营销 | 优惠券 + 满减 + 分摊快照 | 秒杀、红包、会员价、积分 |

### 1.2 分层架构

| 层 | 包 | 职责 | 约束 |
|---|---|---|---|
| 接口层 | `interfaces` | Controller、DTO、VO、参数校验 | 不写业务逻辑，不直接调 Mapper |
| 应用层 | `application` | 用例编排、事务边界、幂等入口 | 一个用例一个事务；外部调用放事务后 |
| 领域层 | `domain` | 状态机、策略、金额计算、实体 | 不依赖 Spring Web、MQ、Redis |
| 基础设施层 | `infrastructure` | Mapper、Repository、MQ、缓存、支付网关 | 实现领域端口，不反向依赖应用层 |
| 公共层 | `common` | 统一响应、异常、TraceId、锁、幂等 | 不包含业务规则 |

依赖方向：`interfaces → application → domain`；`infrastructure` 实现 `domain` 定义的端口。禁止 Controller 直接调用 Mapper，禁止领域层调用支付渠道。

### 1.4 中间件职责

| 中间件 | 职责 | 禁止事项 |
|---|---|---|
| MySQL | 订单、库存、券、支付、退款、结算的唯一事实来源 | 不把 Redis 当库存真相 |
| Redis | 缓存、分布式锁、秒杀预扣 | 不存唯一业务状态 |
| RabbitMQ | 异步事件、Outbox 投递、延迟任务 | 不在事务内等待 MQ 确认 |
| MinIO | 图片、证件、小票 | 不存业务数据 |
| WebSocket | 订单节点、派单通知 | 不作为消息唯一通道，需站内信兜底 |
| Nginx | 静态资源、反向代理 | 不承担业务鉴权 |

### 1.5 部署拓扑

```text
[用户 App/H5] [骑手 App] [商家 App/Web] [运营后台]
        \          |            |             /
         +---------+------------+------------+
                           |
                        [Nginx]
                           |
                 [Spring Boot 3 单体]
                /        |       |       \
          [MySQL 8]  [Redis]  [RabbitMQ]  [MinIO]
```

P0 单实例部署，Docker Compose 启动 MySQL、Redis、RabbitMQ、MinIO 和应用。P1 再把应用无状态化、增加实例和 Nginx 负载均衡。

### 1.6 关键设计决策

| 决策 | 结论 | 原因 |
|---|---|---|
| 分布式事务 | 本地事务 + Outbox，不用 Seata/XA | 练手项目不引入额外中间件；最终一致性足够 |
| 库存真相 | MySQL 条件更新 | Redis 预扣只做秒杀削峰，不能作为最终库存 |
| 状态更新 | `WHERE status = 原状态` + `version` | 防止并发覆盖和重复流转 |
| 异常处理 | `exception_type` 标记，不设订单主状态 | 避免“异常即卡死”，订单保留履约状态 |
| 配送单时点 | 支付成功即生成，状态待派单 | 派单失败、改派、异常池都有单据可挂 |
| 配送单数量 | 一份订单一条，改派更新骑手 | 避免多条“有效”配送单 |
| 结算周期 | T+1 出账、`after_sales_days` 后可结算 | 解决 SRS 中 T+1 与 7 天冻结冲突 |
| 履约服务费 | P0 固定 0，P1 启用 | 降低 P0 结算复杂度 |
| 组合支付 | P0 单通道，P1 扩展 | 避免支付单与退款拆分复杂化 |
| 优惠券退款 | 全额退款未过期才退回，部分退款不退 | 规则可复算，避免二次争议 |
| 外键 | 不建 | 应用层保证，避免迁移与批量写入阻塞 |

### 1.7 非功能约束

| 指标 | P0 目标 | 说明 |
|---|---|---|
| 读接口 P95 | ≤ 300ms | 单机 Docker 环境 |
| 写接口 P95 | ≤ 500ms | 不包含支付渠道耗时 |
| 订单创建 | ≥ 100 单/分钟 | 本地压测 |
| 秒杀/抢单 | ≥ 200 QPS，无超卖 | P1 秒杀，P0 抢单 |
| 骑手在线 | 200 人稳定上报 | 5~10 秒一次 |
| 消息延迟 | ≤ 2s | WebSocket 长连接 |
| 多端状态一致 | ≤ 3s | 订单状态以 DB 为准 |
| 日志 | 结构化，带 TraceId | 不输出未捕获堆栈 |
| 备份 | 每日全量 + 增量 | 至少一次恢复演练 |

## 2. 数据库设计与建表 SQL

### 2.1 设计约定

| 项 | 约定 |
|---|---|
| 引擎/字符集 | InnoDB，`utf8mb4`，`utf8mb4_0900_ai_ci` |
| 金额 | `bigint`，单位分，禁止 `decimal`/`double` 存金额 |
| 费率 | `decimal(6,4)`，6% 存 `0.0600` |
| 状态 | `tinyint`，取值见建表注释与第 3 章 |
| 时间 | `datetime(3)` |
| ID | `bigint unsigned`，应用层生成或自增 |
| JSON | MySQL 8 `json`，只存快照与分摊结果 |
| 外键 | 不建，应用层保证一致性 |
| 删除 | 订单、支付、退款、结算不做逻辑删除；配置表可加 `deleted` |
| 并发 | 状态更新必须条件更新；关键表加 `version` |
| 迁移 | Flyway，禁止手工改生产表结构 |
| 命名 | 表 `t_` 前缀，字段 `snake_case`，索引 `idx_`，唯一键 `uk_` |

### 2.2 核心实体关系

| 主实体 | 关系 | 从实体 | 说明 |
|---|---|---|---|
| 订单 `t_order` | 1:N | 订单明细 `t_order_item` | 商品快照与分摊金额 |
| 订单 | 1:N | 优惠快照 `t_order_discount` | 券、满减、自取立减 |
| 订单 | 1:N | 状态流水 `t_order_status_log` | 每次转换一条 |
| 订单 | 1:0..1 | 配送单 `t_delivery_order` | 仅配送单 |
| 订单 | 1:N | 支付单 `t_payment_order` | P0 通常 1 条，P1 组合支付多条 |
| 订单 | 1:N | 退款单 `t_refund_order` | 多次部分退款 |
| 退款单 | 1:N | 退款明细 `t_refund_item` | 按订单明细退 |
| 券模板 | 1:N | 用户券 `t_user_coupon` | 发放记录 |
| 结算账单 | 1:N | 结算明细 `t_settlement_item` | 商品、佣金、退款、调整 |
| 配送单 | 1:N | 派单记录 `t_dispatch_record` | 每次推送/接受/拒绝 |
| 配送单 | 1:1 | 骑手收入 `t_rider_income` | 一单一条收入 |
| 订单 | 1:N | 异常记录 `t_order_exception` | 无骑手、联系不上等 |

## 3. 核心业务伪代码与状态机

### 3.1 订单状态模型

退款状态、异常标记不得混入订单主状态。

#### 3.1.1 订单状态 `t_order.status`

| 值 | 枚举 | 适用履约 | 是否终态 |
|---|---|---|---|
| 0 | `WAIT_PAY` | 配送/自取 | 否 |
| 10 | `WAIT_ACCEPT` | 配送/自取 | 否 |
| 20 | `PREPARING` | 配送/自取 | 否 |
| 30 | `WAIT_RIDER_PICKUP` | 配送 | 否 |
| 31 | `WAIT_USER_PICKUP` | 自取 | 否 |
| 40 | `DELIVERING` | 配送 | 否 |
| 50 | `DELIVERED` | 配送 | 否 |
| 51 | `PICKED_UP` | 自取 | 否 |
| 60 | `COMPLETED` | 配送/自取 | 是 |
| 70 | `CANCELLED` | 配送/自取 | 是 |

异常不作为订单主状态，统一用 `exception_type` 标记并写入 `t_order_exception`；订单保留原履约状态，避免“异常即卡死”。

#### 3.1.2 辅助状态字段

| 字段 | 类型 | 取值 |
|---|---|---|
| `fulfillment_type` | `tinyint` | 1 配送、2 自取 |
| `payment_status` | `tinyint` | 0 未支付、1 已支付、2 已退款、3 部分退款 |
| `refund_status` | `tinyint` | 0 无退款、1 部分退款、2 全额退款 |
| `exception_type` | `tinyint` | 0 无、1 无骑手、2 联系不上用户、3 地址异常、4 餐品破损、5 商家超时、6 自取超时、7 其他 |
| `settlement_status` | `tinyint` | 0 待结算、1 已结算、2 冻结 |

`refund_status` 只在退款成功后更新；退款中的状态以 `t_refund_order.status` 为准。`exception_type` 只做标记，订单仍保留原履约状态。

### 3.2 订单转换表

Guard 不通过时必须抛业务异常，禁止静默改状态。所有转换在本地事务内完成，外部调用放到事务提交后。

| From | Event | Guard | To | 同事务副作用 |
|---|---|---|---|---|
| — | `CREATE` | 库存锁定成功、券锁定成功 | 0 | 订单、明细、优惠快照、状态流水、库存锁定 |
| 0 | `PAY_SUCCESS` | 支付单金额一致、订单未取消 | 10 | `payment_status=1`、库存锁定转已售、券核销、生成配送单（仅配送） |

| 20 | `PREPARE_DONE` | `fulfillment_type=1` | 30 | 通知派单 |
| 20 | `PREPARE_DONE` | `fulfillment_type=2` | 31 | 生成取餐码、推送备餐完成 |
| 30 | `RIDER_PICKUP` | 配送单已接单、取货码匹配 | 40 | 配送单转配送中 |
| 31 | `PICKUP_VERIFY` | 取餐码匹配、商家或用户身份 | 51 | 取餐码置已用、写 `picked_up_at` |
| 40 | `RIDER_DELIVERED` | 配送单匹配 | 50 | 记录送达时间、启动自动完成计时 |
| 50 | `USER_CONFIRM` / `AUTO_COMPLETE` | 已送达 | 60 | 写 `completed_at`、`settle_eligible_at` |
| 51 | `PICKUP_COMPLETE` | 已取餐 | 60 | 写 `completed_at`、`settle_eligible_at` |
| 51 | `AUTO_COMPLETE` | 已取餐且超时 | 60 | 写 `completed_at`、`settle_eligible_at` |
| 10/20/30/31/40 | `PLATFORM_CANCEL` | 平台角色、填写原因 | 70 | 退款、回补库存、退券、配送单取消 |
| 任意非终态 | `FORCE_COMPLETE` | 平台角色、填写原因 | 60 | 审计日志、结算标记 |
| 10/20/30/31/40/50/51 | `REFUND_FULL_SUCCESS` | 退款单已批准、平台或商家发起、订单未完成 | 70 | 库存/券回滚、退款状态满额 |
| 31 | `PICKUP_TIMEOUT` | 商家已备餐完成 | 60 | 自动完成，货款归商家 |
| 31 | `PICKUP_TIMEOUT` | 商家未备餐完成 | 70 | 全额退款、回补库存、退券 |

订单已是 60 时发生全额退款，只更新 `refund_status=2` 和结算负项，不再调用 `transit`；终态不允许重新打开。`LATE_PAY` 不进入状态机，由支付回调直接生成退款单。40/50 状态发生全额退款时，同时生成骑手补偿记录，避免结算漏项。

所有转换同时写 `version = version + 1`、`updated_at`、`t_order_status_log`；完成写 `completed_at` 和 `settle_eligible_at = completed_at + after_sales_days`，取消写 `cancelled_at`，支付成功写 `payment_status=1`。

### 3.5 退款与资产回滚

| 场景 | 退款金额 | 库存 | 优惠券 | 佣金 | 结算 |
|---|---|---|---|---|---|
| 未支付取消 | 0 | 释放锁定 | 释放 | 0 | 不生成 |
| 商家拒单 | 用户实付 | 回补 | 退券 | 0 | 不生成 |
| 接单前用户取消 | 用户实付 | 回补 | 退券 | 0 | 不生成 |
| 备餐中用户取消 | 按规则，默认全额 | 不回补 | 退券 | 0 | 不生成 |
| 配送中 | 不允许，转售后 | — | — | — | — |
| 送达后全额退款 | 用户实付 | 不回补 | 未过期退券 | 冲回 | 负项 |
| 送达后部分退款 | 商品实付份额 | 不回补 | 不退 | 按退款额冲回 | 负项 |
| 自取超时未取 | 按策略 | 不回补 | 按策略 | 0 或冲回 | 负项 |
| 迟到支付 | 用户实付 | 不回补 | 不退 | 0 | 不生成 |

退款金额计算：

```text
item_refund_amount = round(item.payable_amount * refund_qty / item.quantity)
最后一次退款金额 = item.payable_amount - item.refunded_amount
累计退款金额 <= item.payable_amount
```

配送费退款：骑手未取货，退全额；骑手已取货，不退。打包费按商品退款比例退。

商品退款累计更新必须条件更新：`WHERE refunded_qty + #{qty} <= quantity`。并发退款以订单行锁加条件更新为准，影响行数为 0 返回 `REFUND_AMOUNT_EXCEEDED`，不能先查再写。

### 3.6 优惠券回滚规则

| 阶段 | 券状态 | 动作 | 条件 |
|---|---|---|---|
| 提交订单 | 0 未使用 → 1 已锁定 | 写入 `order_id` | 条件更新成功，否则 `COUPON_LOCK_FAILED` |
| 支付成功 | 1 → 2 已使用 | 写入 `used_at` | 订单状态 0 → 10 同事务 |
| 取消/超时 | 1 → 0 | 清空 `order_id` | 仅未使用券 |
| 全额退款且未过期 | 2 → 0 | 清空 `order_id`、`used_at` | `expire_at > now()` |
| 全额退款且已过期 | 2 → 5 已退款 | 不退券，记损失 | `expire_at <= now()` |
| 部分退款 | 保持 2 | 不退券、不重新校验门槛 | — |
| 订单关闭 | 1 → 0 | 定时任务兜底 | 锁定超过 15 分钟 |

```sql
-- 锁定
UPDATE t_user_coupon
SET status = 1, order_id = #{orderId}, locked_at = NOW(3), version = version + 1
WHERE id = #{couponId} AND user_id = #{userId}
  AND status = 0 AND expire_at > NOW(3);

-- 核销
UPDATE t_user_coupon
SET status = 2, used_at = NOW(3), version = version + 1
WHERE id = #{couponId} AND order_id = #{orderId} AND status = 1;

-- 释放
UPDATE t_user_coupon
SET status = 0, order_id = NULL, locked_at = NULL, version = version + 1
WHERE id = #{couponId} AND order_id = #{orderId} AND status = 1;

-- 退款回滚
UPDATE t_user_coupon
SET status = 0, order_id = NULL, used_at = NULL, version = version + 1
WHERE id = #{couponId} AND order_id = #{orderId} AND status = 2
  AND expire_at > NOW(3);
-- 影响行数为 0 时，置为 5 已退款
```

分摊快照写入 `t_order_item` 和 `t_order_discount.apportion_json`。退款、结算、商家对账只读快照，不重新跑优惠规则。

```text
share = round(discount_amount * item_payable_amount / total_payable_amount)
余数 = discount_amount - sum(share)，加到金额最大的商品
```

| 阶段 | `available_qty` | `locked_qty` | `sold_qty` | 说明 |
|---|---|---|---|---|
| 提交订单 | −qty | +qty | — | 条件更新，失败抛 `STOCK_NOT_ENOUGH` |
| 支付成功 | — | −qty | +qty | 锁定转已售 |

### 3.8 支付回调与晚到支付

支付单状态：0 `INIT`、10 `PAYING`、20 `SUCCESS`、30 `FAIL`、40 `CLOSED`、50 `REFUNDING`、60 `REFUNDED`、61 `PARTIAL_REFUNDED`。

```java
@Transactional(rollbackFor = Exception.class)
public String handlePayCallback(ChannelCallback cb) {
    verifySign(cb);

    PaymentOrder p = paymentMapper.selectByChannelTradeNoForUpdate(cb.channel(), cb.tradeNo());
    if (p == null) throw new BizException("PAYMENT_NOT_FOUND");
    if (p.getStatus() == PaymentStatus.SUCCESS) return "success";   // 重复回调

    if (!p.getAmount().equals(cb.amount())) {                        // 金额篡改
        log.error("pay amount mismatch payment={} expect={} actual={}",
                  p.getPaymentNo(), p.getAmount(), cb.amount());
        return "fail";
    }

    int rows = paymentMapper.markSuccess(p.getId(), cb.tradeNo(), now());
    if (rows != 1) return "success";                                 // 并发回调

    Order order = orderMapper.selectForUpdate(p.getOrderId());
    if (order.getStatus() == OrderStatus.CANCELLED) {
        refundService.createLatePayRefund(order, p);                 // 迟到支付
    } else {
        orderStateMachine.transit(order.getId(), PAY_SUCCESS, SYSTEM, cb.tradeNo());
    }
    outboxService.append(order.getId(), "PAY_SUCCESS");
    return "success";
}
```

超时关单任务：扫描 `t_payment_order status IN (0,10) AND created_at < now()-15min`，条件更新为 `CLOSED`，订单 `0 → 70`，释放库存和券。

### 3.10 结算与抽佣

#### 3.10.1 双时钟

| 概念 | 规则 |
|---|---|
| `bill_generate_at` | 每日 02:00 |
| `bill_period` | 前一日 00:00–24:00 |
| `after_sales_days` | 默认 7 天，后台可配 |
| `settle_eligible_at` | `completed_at + after_sales_days` |
| 入账条件 | `status=COMPLETED` 且 `settle_eligible_at <= now()` 且无未结售后单 |
| 账单归属 | 按 `settle_eligible_at` 归属，不按 `completed_at`；任务扫描 `settle_eligible_at < period_end AND settlement_status=0`，漏单进入下一期 |

“T+1”只能指账单生成时间，不能指到账时间。若坚持 T+1 到账，必须把 `after_sales_days` 配为 0 或 1，并在文档中删除“7 天售后期”。

#### 3.10.2 商家结算公式

`gross_amount` 含商品金额和打包费，不含配送费。配送费归平台，再由平台付给骑手。

```text
commission_base   = gross_amount - merchant_discount
commission_amount = round(commission_base * commission_rate)

payable_amount = gross_amount
               - merchant_discount
               + platform_discount
               - commission_amount
               - performance_fee
               - refund_amount
```

| 项 | 定义 | 符号 |
|---|---|---|
| `gross_amount` | `Σ item.original_amount + packaging_fee` | + |
| `merchant_discount` | 商家券、商家满减、自取立减中商家承担部分 | − |
| `platform_discount` | 平台券、平台满减中平台承担部分 | + |
| `commission_amount` | 技术服务费 | − |
| `performance_fee` | P0 固定 0，P1 启用 | − |
| `refund_amount` | 本期成功退款中属于该订单的金额 | − |

`payable_amount < 0` 时不在本期扣款，生成 `carry_forward_amount` 进入下一期负项；连续两期为负转人工。

#### 3.10.3 结算示例（单位：分）

```text
商品 10000 + 打包 200 = gross 10200
商家券 1000（商家承担）
平台券 500（平台承担）
配送费 500（用户付，平台收，付骑手）
佣金率 6%，commission_base = 10200 - 1000 = 9200
commission = 9200 * 6% = 552
商家应结 = 10200 - 1000 + 500 - 552 = 9148
用户实付 = 10200 - 1000 - 500 + 500 = 9200
平台净额 = 552 + 500 - 500 - 500 = 52
```

#### 3.10.4 退款冲抵

已结算订单退款，生成 `t_settlement_item(item_type=4, amount=-refundAmount)` 挂到下一期账单；下一期不存在时先建调整账单。佣金冲回按 `round(refundGoodsAmount * appliedRate)` 计算。

账单生成后不可修改。退款成功时间在 `period_end` 之前的计入本期，之后的进入下一期调整单；同一订单的商品结算项只允许出现在一张正式账单中，退款调整项可出现在后续账单。

```java
@Transactional(rollbackFor = Exception.class)
public CreateOrderResp createOrder(CreateOrderCmd cmd, String idemKey) {
    IdemResult idem = idempotencyService.beginInNewTx(idemKey, "CREATE_ORDER", cmd);
    if (idem.isReplay()) return idem.response();
    if (idem.isProcessing()) throw new BizException("REQUEST_IN_PROGRESS");

    validateFulfillment(cmd);          // 配送校验地址/围栏；自取校验手机号
    validateSku(cmd);                  // 上架、估清、限购

    Order order = buildOrder(cmd);     // status = WAIT_PAY, pay_amount 先算
    orderMapper.insert(order);

    List<OrderItem> items = buildItems(order, cmd);
    itemMapper.batchInsert(items);

    List<OrderDiscount> discounts =
        discountService.lockAndBuild(order, items, cmd.getCouponId(), cmd.getPromotionId());
    discountMapper.batchInsert(discounts);

    stockService.lock(order, items);   // 按 sku_id 升序
    statusLogService.log(order, null, WAIT_PAY, "CREATE", cmd.operator());
    outboxService.append(order.getId(), "ORDER_CREATED");

    CreateOrderResp resp = toResp(order);
    idempotencyService.success(idemKey, order.getId(), resp);
    return resp;
}
```

业务失败时本地事务回滚，`t_idempotency` 的占位记录由独立事务更新为失败（`failInNewTx`）；客户端用同一键重试即可。`beginInNewTx` 使用 `REQUIRES_NEW`，不能被业务事务回滚带走。

```java
@Transactional(rollbackFor = Exception.class)
```

#### 3.11.3 退款成功回调

```java
@Transactional(rollbackFor = Exception.class)
public void onRefundSuccess(String refundNo, String channelRefundNo) {

    if (r.getStatus() == RefundStatus.SUCCESS) return;             // 幂等

    if (r.getRefundType() == FULL) {
        stockService.refund(r.getOrderId(), r.getItems());
        couponService.rollbackByOrder(r.getOrderId());
        orderMapper.markRefundStatus(r.getOrderId(), REFUND_FULL);
        if (order.getStatus() != OrderStatus.COMPLETED) {
            orderStateMachine.transit(r.getOrderId(), REFUND_FULL_SUCCESS, SYSTEM, refundNo);
        }
    } else {
        orderMapper.markRefundStatus(r.getOrderId(), REFUND_PARTIAL);
    }

    settlementService.appendRefundItem(r);
    outboxService.append(r.getOrderId(), "REFUND_SUCCESS");
}
```

退款失败：`REFUNDING → FAILED`，写重试时间；重试 3 次仍失败转人工，订单退款状态不变。

#### 3.11.6 结算出账

```java
@Scheduled(cron = "0 0 2 * * ?")
public void generateMerchantBill() {
    LocalDate billDate = LocalDate.now().minusDays(1);

    for (Long merchantId : orderMapper.findMerchantIdsForBill(billDate)) {
        String key = "lock:settle:" + merchantId + ":" + billDate;
        if (!lock.tryLock(key, 0, 30, TimeUnit.MINUTES)) continue;

        try {
            List<Order> orders = orderMapper.findSettleEligible(merchantId, billDate);
            if (orders.isEmpty()) continue;

            SettlementBill bill = calculator.build(merchantId, billDate, orders);
            billMapper.insert(bill);                  // 唯一键 merchant_id + bill_date
            itemMapper.batchInsert(bill.getItems());
            orderMapper.markSettled(orders, bill.getId()); // 条件更新 settlement_status 0→1
        } finally {
            lock.unlock(key);
        }
    }
}
```

`findSettleEligible` 必须带 `status=60 AND settle_eligible_at < #{periodEnd} AND settlement_status=0`。`settle_eligible_at` 落在本期或更早的订单都进入本期，避免任务失败导致漏单；`markSettled` 用条件更新，影响行数与订单数不一致时整笔账单回滚。

```java
@Scheduled(fixedDelay = 1000)
```

### 3.12 状态机实现约束

| 约束 | 规则 |
|---|---|
| 唯一入口 | 所有订单状态变更只走 `OrderStateMachine.transit()` |
| 条件更新 | `UPDATE ... WHERE id=? AND status=?`，影响行数 0 抛 `ORDER_CONCURRENT_MODIFIED` |
| 幂等 | `t_order_status_log` 唯一键 `(order_id, request_id)` |
| 终态 | 60/70 不允许回退；退款只改 `refund_status` |
| 角色 | 商家只能操作本店订单；骑手只能操作本人配送单；平台可强制 |
| 事务 | 状态、库存、券、退款单、Outbox 同事务；外部调用事务后 |
| 审计 | 每次转换写 from/to、event、operator、request_id |

## 4. 高并发与数据一致性规范

### 4.1 事务边界

| 操作 | 同一本地事务 | 事务提交后 |
|---|---|---|
| 创建订单 | 库存锁定、券锁定、订单、明细、优惠快照、状态流水 | WebSocket 通知商家 |
| 支付回调 | 支付单成功、订单状态、Outbox | 推送用户/商家 |
| 退款申请 | 退款单、退款明细、Outbox | 调支付渠道退款 |
| 退款回调 | 退款单成功、订单退款状态、库存/券回滚、Outbox | 推送 |
| 取餐码核销 | 订单 31→51、取餐码状态、核销日志、Outbox | 推送 |
| 结算出账 | 账单、明细、订单结算标记 | 通知财务 |

禁止在数据库事务内调用支付宝、微信、WebSocket 等外部服务。

### 4.2 分布式锁

使用 Redisson。锁只用于跨行编排，不替代条件更新。

| 锁键 | 场景 | 等待 | 租期 |
|---|---|---|---|
| `lock:order:{orderId}` | 订单状态流转 | 3s | 30s |
| `lock:stock:{shopId}:{skuId}` | 单 SKU 批量扣减 | 3s | 30s |
| `lock:coupon:{userCouponId}` | 券锁定/回滚 | 3s | 30s |
| `lock:dispatch:{deliveryOrderId}` | 派单/抢单 | 1s | 15s |
| `lock:pickup:{orderId}` | 取餐码核销 | 1s | 15s |
| `lock:settle:{merchantId}:{billDate}` | 结算出账 | 0s | 30min |

加锁顺序：订单 → 库存（`sku_id` 升序）→ 优惠券；禁止反向加锁。锁等待超时返回 409 `LOCK_TIMEOUT`，不无限阻塞。

### 4.3 接口幂等键

| 项 | 规则 |
|---|---|
| 客户端写接口 | Header `Idempotency-Key: {uuid}`，下单、支付、退款、核销必带 |
| 服务端存储键 | `biz_type + ":" + idempotency_key` |
| 表 | `t_idempotency`，唯一键 `idempotency_key` |
| 请求指纹 | `request_hash = SHA-256(method + path + sorted_body)` |
| 同键不同参数 | 返回 409 `IDEMPOTENCY_KEY_REUSED` |
| 处理中重复请求 | 返回 409 `REQUEST_IN_PROGRESS`，客户端 1 秒后重试 |
| 成功响应 | 落库 `response_code`、`response_body`，后续请求直接返回 |
| TTL | 普通写接口 24 小时；支付/退款 7 天 |
| 内部任务 | 使用业务唯一键作为 `request_id`：`PAY:{channelTradeNo}`、`REFUND:{refundNo}`、`PICKUP:{orderId}:{code}` |

幂等占位记录用独立事务（`REQUIRES_NEW`）提交；业务失败时把 `status` 更新为 2，不能随业务事务回滚。否则并发重复请求看不到“处理中”状态，唯一键冲突也无法区分重复请求。DB 唯一约束是最后一道防线，不能只依赖 Redis 幂等。

### 4.4 防重与条件更新

| 机制 | 用法 | 失败返回 |
|---|---|---|
| 条件更新 | `UPDATE ... WHERE status = 原状态` | 影响行数 0，抛并发异常 |
| 乐观锁 | `version = version + 1` + `WHERE version = ?` | `ORDER_CONCURRENT_MODIFIED` |
| 唯一键 | 支付渠道交易号、退款单号、状态流水 `request_id` | `DUPLICATE_REQUEST` |
| 幂等表 | `t_idempotency` | `REQUEST_IN_PROGRESS` |
| 分布式锁 | 跨行编排 | `LOCK_TIMEOUT` |

禁止先 `SELECT` 再无条件 `UPDATE`。所有“检查后写入”必须落成一条带条件的 SQL，或以行锁包住。

### 4.5 库存并发

| 场景 | 机制 |
|---|---|
| 普通下单 | DB 条件更新 `available_qty >= qty`，失败抛 `STOCK_NOT_ENOUGH` |
| 多 SKU 订单 | 按 `sku_id` 升序更新；任一失败整单回滚 |
| 取消/超时 | `t_stock_lock` 条件更新 `0 → 2`，成功后再回补库存 |
| 退款 | `restock_flag=1` 才回补；`sold_qty` 条件更新 |
| 秒杀 P1 | Redis Lua 预扣 + 用户去重；DB 条件更新最终兜底 |
| 估清 | `sold_out=1`，下单前拦截 |

库存日志唯一键 `(biz_type, biz_id, sku_id, op)` 保证重复消费只生效一次。

### 4.6 缓存与消息一致性

| 项 | 规则 |
|---|---|
| 缓存 | 订单状态以 DB 为准；缓存只读加速，更新后删除缓存 |
| 删除时机 | 事务提交后删除，禁止事务内删 |
| WebSocket | 事务提交后推送；消息带 `version` |
| Outbox | 与业务同事务落库，事务后投递 |
| 消费端 | 按 `event_id` 幂等；重复消息不重复处理 |
| 多端一致 | 前端按 `version` 丢弃旧消息；必要时主动查询 |

### 4.7 并发场景清单

| 场景 | 预期 |
|---|---|
| 同一 `Idempotency-Key` 重复下单 | 只生成 1 个订单，库存只锁 1 次 |
| 库存 10，100 并发下单 | 成功 10，失败 90，不超卖 |
| 支付回调与取消并发 | 取消后支付成功 → 迟到支付退款；支付成功后取消 → 正常退款 |
| 支付回调重复 5 次 | 订单只流转一次 |
| 多个骑手同时抢单 | 只有一个条件更新成功 |
| 取餐码重复核销 | 第一次成功，第二次返回已核销 |
| 并发部分退款 | 累计退款不超过 `item.payable_amount` |
| 结算任务重复执行 | 唯一键 `(merchant_id, bill_date)` 拦截，订单只结算一次 |
| Outbox 重复投递 | 消费端按 `event_id` 幂等 |
| 退款与结算并发 | 账单生成后不可改，退款进入下一期调整 |

## 5. 异常处理与分布式事务兜底策略

### 5.1 异常分类

| 类型 | 示例 | 处理 |
|---|---|---|
| 业务异常 | 库存不足、状态不允许、券不可用 | 不重试，返回业务码 |
| 并发异常 | 条件更新 0 行、锁超时 | 返回 409，客户端可重试一次 |
| 渠道异常 | 支付宝超时、退款失败 | 状态置中间态，后台重试 |
| 基础设施异常 | DB 连接失败、MQ 不可用 | 事务回滚，告警，客户端重试 |
| 数据不一致 | 支付成功但订单未更新、账单差异 | 对账任务 + 人工处理 |

### 5.2 本地事务失败

- 业务事务回滚，状态、库存、券、退款单、Outbox 一起回滚。
- 幂等占位记录用独立事务；业务失败时更新为 `status=2`，不能被业务回滚带走。
- 事务内禁止调用支付、MQ、WebSocket。
- 捕获 `DuplicateKeyException` 转成业务码，不向前端抛原始堆栈。

### 5.3 外部调用失败

| 场景 | 状态 | 补偿 |
|---|---|---|
| 创建支付单失败 | 订单 0，支付单 30 | 用户重试；超时关单 |
| 支付回调丢失 | 支付单 10 | 主动查询渠道；15 分钟关单 |
| 退款调用失败 | 退款单 20 | 指数退避重试 3 次，转人工 |
| 退款回调丢失 | 退款单 20 | 主动查询渠道，定时补偿 |
| WebSocket 推送失败 | 业务已提交 | Outbox 重试；站内信兜底 |

### 5.4 Outbox 与消息补偿

| 项 | 规则 |
|---|---|
| 写入 | 与业务同事务写 `t_outbox_event` |
| 投递 | 定时任务扫描 `status=0`，每次 100 条 |
| 重试 | 指数退避：1s、5s、30s、5min、30min |
| 失败 | `status=2`，告警，人工重放 |
| 消费 | 按 `event_id` 幂等，重复消息直接 ACK |
| 顺序 | 同一 `aggregate_id` 尽量串行；不保证全局顺序 |

### 5.5 定时任务兜底

| 任务 | 周期 | 作用 |
|---|---|---|
| `OrderTimeoutJob` | 1 分钟 | 关闭 15 分钟未支付订单，释放库存/券 |
| `StockReleaseJob` | 30 秒 | 释放过期库存锁定 |
| `CouponReleaseJob` | 1 分钟 | 释放过期券锁定 |
| `AutoCompleteJob` | 5 分钟 | 配送送达后自动完成；自取超时处理 |
| `DispatchRetryJob` | 15 秒 | 重新派单、超时转异常池 |
| `SettlementJob` | 每日 02:00 | 生成商家账单 |
| `RiderSettlementJob` | 每日 02:30 | 生成骑手收入账单 |
| `OutboxRelayJob` | 1 秒 | 投递 Outbox |
| `ReconJob` | 每日 03:00 | 支付/退款/结算对账 |
| `PayoutRetryJob` | 10 分钟 | 重试失败提现 |

所有任务使用分布式锁 + 条件更新，保证多实例只执行一次。

### 5.6 人工兜底

| 场景 | 入口 | 动作 |
|---|---|---|
| 无骑手 | 异常订单池 | 手动派单、取消退款、补偿 |
| 骑手取货后异常 | 异常订单池 | 平台介入、退款/完成、骑手补偿 |
| 退款失败 | 退款管理 | 重试、换通道、线下处理 |
| 结算差异 | 结算单 | 生成调整单，不改历史账单 |
| 支付对账差异 | 对账页 | 记录差异、人工核对、补单/退款 |
| 数据修复 | 后台工具 | 必须审批 + 审计日志 |

### 5.7 对账与审计

| 对账项 | 频率 | 差异处理 |
|---|---|---|
| 支付单 vs 渠道流水 | 每日 | 生成差异记录，人工核对 |
| 退款单 vs 渠道退款 | 每日 | 重试或人工退款 |
| 订单 vs 支付单 | 每日 | 补状态、补退款 |
| 结算账单 vs 订单 | 每日 | 调整单，不改历史账单 |
| 骑手收入 vs 配送单 | 每日 | 补收入、扣罚款 |
| 库存流水 vs 库存余额 | 每周 | 盘点、修正、审计 |

审计要求：订单改价、退款、结算、派单、权限变更写操作日志，包含操作人、角色、时间、对象、IP、TraceId。

### 5.8 故障演练清单

| 演练 | 预期 |
|---|---|
| 杀 MQ | 业务提交成功，Outbox 积压，恢复后补发 |
