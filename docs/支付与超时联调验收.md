# 支付成功与支付超时联调验收

> 接口：`POST /api/v1/payments/pay`、`POST /api/v1/payments/callback`
> 异步消息：RabbitMQ `order.exchange` / `order.pay.success` / `order.timeout`
> 测试环境：MySQL 3307、Redis 6379、RabbitMQ 5672

## 1. 配置

`application.yml` 新增：

```yaml
app:
  order:
    timeout-delay-seconds: ${ORDER_TIMEOUT_DELAY_SECONDS:900}
  payment:
    callback-secret: ${PAYMENT_CALLBACK_SECRET:change_me_payment_callback_secret}
```

- 生产/默认：15 分钟（900 秒）。
- 联调：启动时覆盖为 15 秒，避免等待 15 分钟：

```powershell
java -jar solo-eats-app/target/solo-eats-app-1.0.0-SNAPSHOT.jar `
  --app.order.timeout-delay-seconds=15 `
  --app.payment.callback-secret=test-secret-123
```

## 2. 发起支付

```powershell
curl.exe -X POST http://localhost:8080/api/v1/payments/pay `
  -H "Content-Type: application/json" `
  -H "Idempotency-Key: pay-test-001" `
  -d "{ \"orderId\": 2, \"channel\": 3 }"
```

响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "paymentId": 1,
    "paymentNo": "PAY2026102109454081C8A7D5",
    "orderId": 2,
    "channel": 3,
    "amount": 5300,
    "status": 10
  }
}
```

规则：

| 项 | 规则 |
|---|---|
| 订单状态 | 只允许 `WAIT_PAY(0)` |
| 金额 | 取 `t_order.pay_amount`，不信任客户端金额 |
| 支付单状态 | 创建时为 `PAYING(10)` |
| 幂等 | `Idempotency-Key` 与 `t_payment_order.idempotency_key` 唯一键 |
| 活动支付单 | 同一订单已有 `INIT/PAYING` 支付单时直接返回该单 |

## 3. 模拟回调与签名

签名内容：

```text
paymentNo + ":" + tradeNo + ":" + amount
```

算法：HMAC-SHA256，输出小写 hex。

Node 计算示例：

```javascript
const crypto = require('crypto');
const sign = crypto
  .createHmac('sha256', 'test-secret-123')
  .update(`${paymentNo}:${tradeNo}:${amount}`)
  .digest('hex');
```

回调请求：

```powershell
curl.exe -X POST http://localhost:8080/api/v1/payments/callback `
  -H "Content-Type: application/json" `
  -d '{
    "paymentNo": "PAY2026102109454081C8A7D5",
    "tradeNo": "TRADE-A-1792547139",
    "amount": 5300,
    "sign": "<HMAC-SHA256>"
  }'
```

回调处理：

1. 校验签名。
2. 校验支付单存在、金额一致。
3. 条件更新 `t_payment_order.status 10 → 20`，写 `channel_trade_no`、`paid_at`。
4. 已成功支付单重复回调直接返回成功，不重复发消息。
5. 事务提交后发送 `order.pay.success` 到 RabbitMQ。
6. `OrderPaySuccessConsumer` 消费后：
   - 订单 `WAIT_PAY(0) → WAIT_ACCEPT(10)`；
   - `t_sku_stock.locked_qty` 扣减、`sold_qty` 增加；
   - `t_user_coupon.status 1 → 2`；
   - `t_order.payment_status = 1`。

## 4. 支付成功实测结果

| 表 | 结果 |
|---|---|
| `t_order` | status=10，payment_status=1，pay_amount=5300 |
| `t_payment_order` | status=20，channel_trade_no=`TRADE-A-1792547139` |
| `t_sku_stock` | available=98，locked=0，sold=2 |
| `t_user_coupon` | status=2，order_id=2 |
| `t_stock_log` | `ORDER / LOCK / 2 / 100 → 98`、`ORDER / CONFIRM / 2 / 98 → 98` |
| `t_order_status_log` | `0 → 10 / PAY_SUCCESS` |

重复回调第二次返回 200，订单状态日志只有一条 `PAY_SUCCESS`。

## 5. 支付超时取消

下单成功后，`OrderCreatedEvent` 在事务提交后触发：

- 向 `order.exchange` 发送 routing key `order.delay`；
- 消息 TTL = `app.order.timeout-delay-seconds × 1000`；
- `order.delay.queue` 无消费者，TTL 到期后通过 DLX 转发到 `order.timeout`；
- `OrderTimeoutConsumer` 消费后执行：
  1. 订单仍为 `WAIT_PAY(0)` 时，状态机执行 `PAY_TIMEOUT → CANCELLED(70)`；
  2. `StockService.release()`：`locked_qty → available_qty`；
  3. `CouponService.release()`：券状态 `1 → 0`，清空 `order_id`；
  4. 写 `t_stock_log`（`ORDER / RELEASE`）和 `t_order_status_log`（`PAY_TIMEOUT`）。

### 实测结果

订单 B：下单后不支付，15 秒延迟消息到期。

| 表 | 结果 |
|---|---|
| `t_order` | status=70（CANCELLED），payment_status=0 |
| `t_sku_stock` | available=98，locked=0，sold=2（订单 B 释放，订单 A 已售 2） |
| `t_user_coupon` | 3002 status=0，order_id=NULL |
| `t_stock_log` | `ORDER / LOCK / 2 / 98 → 96`、`ORDER / RELEASE / 2 / 96 → 98` |
| `t_order_status_log` | `0 → 70 / PAY_TIMEOUT` |

已支付订单 A 的 15 秒延迟消息到期后，订单仍保持 `WAIT_ACCEPT(10)`，库存和券未被回滚。

## 7. 已知边界

| 项 | 当前处理 | 后续 |
|---|---|---|
| 迟到支付 | 超时取消后支付回调仍可把支付单置成功，订单侧消费者看到 CANCELLED 直接返回 | 增加 `LATE_PAY` 退款单与自动退款 |
| 支付单关闭 | 超时不主动关闭 `t_payment_order` | 增加支付超时关闭任务或事件 |
| 消息可靠性 | 事务提交后直接投递 RabbitMQ，发送失败只记日志 | 接 `t_outbox_event` + 定时重投 |
| 重复回调返回 | 已成功支付单返回 200，不返回首次业务数据 | 支付回调本身幂等，业务侧不重复发消息 |
