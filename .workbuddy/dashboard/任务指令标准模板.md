# 任务指令标准模板（Claude Code 派发 / 回执 / Dashboard 回写）

> 版本：v1.4 · 建立日期：2026-10-22
> 适用：`docs/tasks/T01~T17` 全部任务卡的每一个**会话单元**（阶段）
> 配套文件：`dashboard.html`（进度看板）、`dashboard_update.py`（回写工具）——**与本文件同处 `.workbuddy/dashboard/`**
> 角色分工：**WorkBuddy＝派发方 + 唯一回写方**；**Claude Code＝执行方**；**Git 历史＝事实来源**

> ⚠️ **本目录是本地工作区，与项目代码完全隔离，永不入库**：
> `.workbuddy/dashboard/`（本文件 + 看板 + 回写脚本）、`.workbuddy/receipts/`（回执）、`.workbuddy/memory/`（会话记忆）
> 全部被 `.gitignore` 的 `.workbuddy/` 一条覆盖。仓库里 `git ls-files .workbuddy` 必须为空。
> **禁止 `git add` / `git commit` / `git push`**；项目完工后整目录删除，无需清理提交历史。
> 看板相关的任何内容**只允许存在于本目录**，不得写进 `CLAUDE.md`、`docs/tasks/README.md`、`scripts/`（那些是交付物）。

## 0. 一句话规则

> Claude Code 只写**代码 + 任务卡执行记录 + 回执 JSON**，
> **绝不直接改 `.workbuddy/dashboard/dashboard.html`**；看板由 WorkBuddy 依据回执自动回写。

这样做的原因：一个会话可能被用户中断、可能编译失败、可能只提交了一半。若 Claude Code 直接写看板，会出现「三处口径不一致」（代码 / 任务卡 / 看板）。把看板收敛到单一写入方，才能保证「点开页面看到的就是仓库真实状态」。

补充：看板**只存本地**。它的定位是「开发期望远镜」，不是交付物——写入 `.gitignore`，不参与任何 commit / push，
项目完工后随 `.workbuddy/` 一起删除。

## 1. 派发模板（WorkBuddy → Claude Code 的 Prompt 骨架）

> 复制后替换 `<...>`。一次派发**只能是一个会话单元**（例：`T03 阶段A`），不得合并两个阶段。

```text
你在仓库 D:\codes\SoloEats 中执行 SoloEats 任务卡的单个会话单元。

【本次范围】<T03> 阶段<A> —— <一句话目标，如：MinIO 文件服务 + /api/v1/files 上传下载>
【禁止扩张】只做该阶段文件清单内的改动。不得顺手重构、不得改代码风格、不得升级依赖版本。

【开始前必读，按顺序】
1) CLAUDE.md（项目约定，唯一约定入口）
2) docs/tasks/README.md（任务总表 + 全局共享知识 + 执行约定）
3) docs/tasks/<T03>-*.md 全文（目标 / 数据模型 / 接口 / 文件清单 / 约束 / 验收 / 禁止 / 执行记录）
4) 卡内「前置依赖」列出的既有类（用 Read 打开真实代码确认，不凭记忆）
5) .workbuddy/dashboard/dashboard.html 仅作现状参考——**不得修改此文件**

【硬约束（摘自 CLAUDE.md，逐条遵守）】
- 金额 bigint 分 / Java long；禁止 double/float
- 响应 ApiResponse<T>{code,message,data,traceId}；分页 PageResult<T>
- 异常抛 BizException(ErrorCode)，错误码只能追加
- 状态流转用条件更新 WHERE id=? AND status=?，禁止先 SELECT 再 UPDATE
- 写接口加 @Idempotent(key=..., ttlSeconds=...)（该注解**没有** bizType 属性）
- 新表带 tenant_id / created_at / updated_at，只增不改（Expand-Contract）
- Controller/DTO/VO 一律放 solo-eats-app；领域模块只放 domain/mapper/service
- 不得删除或修改既有测试

【完成前自检（必须真实执行并记录原始输出）】
1) mvn -q -pl solo-eats-<module> -am compile        → 0 error
2) mvn -q -DskipTests package                        → BUILD SUCCESS
3) 涉及前端：cd solo-eats-web && npm run build        → dist 生成成功
4) 新增核心 service 至少 1 个 Mockito 单测；既有测试全绿

【收尾（两件事，缺一不可）】
A. 回写任务卡「执行记录」表格一行：日期 / 会话范围 / 新增修改文件数 / 编译结果 / 遗留问题
B. 一个会话单元一个 commit，信息格式：feat(T03-A): MinIO 文件服务与上传接口
   然后按第 2 节格式输出 RECEIPT JSON（控制台最后一段，必须可被 JSON.parse）

【遇到冲突时】
任务卡「禁止事项」与需求冲突 → 停下来，把冲突写进「遗留问题」并输出 status="doing" 的回执，不要擅自突破。
```

## 2. 完成回执（RECEIPT JSON）规范

**落盘位置**：`.workbuddy/receipts/<卡号>-<阶段>.json`（例：`.workbuddy/receipts/T03-A.json`）
**输出时机**：无论成功 / 编译失败 / 被中断，**都必须输出**。

| 字段 | 必填 | 说明 |
|---|---|---|
| `card` | ✅ | 任务卡号，如 `"T03"`；必须是 T01~T17 之一 |
| `stage` | ✅ | 阶段标识：`"A"` / `"B"` / `"C"` / `"A-0"` / `"0"~"4"`（T17 批次）。单段卡统一填 `"A"` |
| `status` | ✅ | `done` / `doing` / `todo` / `fail`（`fail` 会被归一为「进行中 + 构建失败」） |
| `commit` | 建议 | 短 hash，7 位；未提交填 `null` 并在 issues 说明 |
| `commitMsg` | 建议 | 提交信息原文 |
| `maven` | ✅ | `{"result":"pass|fail|skip","detail":"BUILD SUCCESS · 10 模块 · 38s"}` |
| `tests` | 建议 | 如 `"12 passed"`、`"Tests run: 12, Failures: 0"` |
| `files` | 建议 | `{"added":18,"modified":6,"deleted":0}` |
| `migrations` | 建议 | `["V7__merchant_onboarding.sql"]` |
| `issues` | ✅ | 遗留问题数组，**覆盖式**写入（本次为准，不要把历史问题丢光） |
| `front` | 仅前端 | `{"end":"平台运营后台","delta":2}`：该端新增页数 |
| `log` | 建议 | `{"type":"feat|fix|docs|audit|doing","title":"...","detail":"..."}` |
| `baseline` | 可选 | `"main@9f2c1ab"`，覆盖看板页头基线 |

**示例**

```json
{
  "card": "T03",
  "stage": "A",
  "status": "done",
  "commit": "9f2c1ab",
  "commitMsg": "feat(T03-A): MinIO 文件服务与上传接口",
  "maven": { "result": "pass", "detail": "BUILD SUCCESS · 10 模块 · 38s" },
  "tests": "12 passed",
  "files": { "added": 18, "modified": 6, "deleted": 0 },
  "migrations": ["V7__merchant_onboarding.sql"],
  "issues": ["presign 直传未做分片", "下载接口未做防盗链"],
  "log": { "type": "feat", "title": "T03 阶段A：MinIO 文件服务", "detail": "V7 + FileController + 存储端口抽象" }
}
```

**失败/中断示例**

```json
{
  "card": "T03",
  "stage": "A",
  "status": "fail",
  "commit": null,
  "maven": { "result": "fail", "detail": "solo-eats-app compile 3 error：FileController 缺少 @RequestPart" },
  "issues": ["编译未通过，已保留工作区改动待续做"],
  "log": { "type": "fix", "title": "T03 阶段A 编译失败中断" }
}
```

## 3. Dashboard 回写规则（WorkBuddy 强制职责）

### 3.1 触发时机

下列**任一**情形发生，必须在同一轮回复内回写 `.workbuddy/dashboard/dashboard.html`：

1. Claude Code 会话正常结束（`status=done`）；
2. Claude Code 编译失败 / 报错结束（`status=fail`）；
3. 用户中断 Claude Code（按当时的代码与 git 状态写 `doing`）；
4. 任务卡本身被修改（范围 / 阶段拆分 / 页码口径变化）→ 同步 `srs` 与 `cards[].stages`；
5. 手动 `git commit` / `revert` 改变了某卡的事实状态。

### 3.2 字段映射

| 回执字段 | 写入位置 |
|---|---|
| `card` + `stage` | 定位 `cards[]` → `stages[]`；不存在则追加 |
| `status` | `stages[].s`，并聚合回 `cards[].status` |
| `commit` | `stages[].c` |
| `maven.result / detail` | `cards[].maven = {r,d}` |
| `tests` | `cards[].tests` |
| `issues` | `cards[].issues`（覆盖） |
| `front.end / delta` | `srs.ends[].done` 与 `srs.{admin,merchant}.delivered` |
| `log` | `logs[]` 头部插入（`at`＝当前 CST 时间） |
| `baseline` | `meta.baseline` |
| 每次回写 | `meta.updatedAt` 必更新 |

### 3.3 卡级状态聚合规则

```
全部阶段 done                 → 卡片 done（🟢 已完成）
存在任一 done 或 doing        → 卡片 doing（🟡 进行中）
全部 todo                     → 卡片 todo（🔴 未开始）
```

### 3.4 执行步骤（标准三连）

```bash
# 1) 回执落盘（Claude Code 或 WorkBuddy 写入）
#    .workbuddy/receipts/T03-A.json

# 2) 校验 commit 确实存在（回执里的 hash 必须能在 git log 命中）
git log --oneline -1 9f2c1ab

# 3) 回写看板（自动更新 meta.updatedAt / logs / 状态 / 一致性自检）
python .workbuddy/dashboard/dashboard_update.py --receipt .workbuddy/receipts/T03-A.json --baseline auto

# 4) 复验（JSON 合法 + 状态与阶段一致 + 页数合计对得上）
python .workbuddy/dashboard/dashboard_update.py --check
```

### 3.5 强制约束（违反视为本次会话未完成）

1. **单一写入方**：只有 WorkBuddy 写 `dashboard.html`；Claude Code 一律不得修改（防并发覆盖）。
2. **失败也回流**：编译失败、被中断、未提交，都要写 `doing`/`fail` 回执并在 `issues` 记录阻断点；**禁止只看板写"已完成"**。
3. **数据必须可追溯**：`commit` 必须能在 `git log` 命中；`maven` 结果必须来自真实命令输出；**禁止按推测或按任务卡计划填写**。
4. **口径一致**：看板是视图，任务卡「执行记录」是正本。两者不一致时以任务卡为准，并立刻改看板。
5. **结构区只读**：只维护 `<!-- DATA:BEGIN -->` 与 `<!-- DATA:END -->` 之间的 JSON；不改 HTML/CSS/JS 结构（除新增板块）。
6. **不臆造完成率**：完成率分母固定 = `meta.totalCards`（17 张卡）与 `meta.totalUnits`（36 个会话单元）；新增阶段要同时改这两个值。
7. **本地文件，永不入库**：`.workbuddy/dashboard/dashboard.html` 与整个 `.workbuddy/`（含本文件、回执、脚本）都已在 `.gitignore` 中。提交前用 `git status` 确认它们**不在**待提交列表；若发现被 `git add -f` 强加，立刻 `git rm --cached <路径>` 并复查 `.gitignore`。看板与配套工具都不是交付物，**不进 README 交付清单、不打 tag、不提 PR**。任何看板相关的规则/脚本都只允许放在 `.workbuddy/dashboard/`，**不得写进 `CLAUDE.md`、`docs/tasks/README.md` 或 `scripts/`**。
8. **同步记忆**：回写后在工作区日志 `.workbuddy/memory/YYYY-MM-DD.md` 追加上下文（commit / 阶段 / 遗留）。

### 3.6 验收（每次回写后自检 4 条）

- [ ] `python .workbuddy/dashboard/dashboard_update.py --check` 输出 `[DONE] 校验通过`
- [ ] 页面打开无「数据块解析失败」红色横幅
- [ ] 页头 `最后更新` 时间 = 本次时间，`基线` = 当前 `main@<short hash>`
- [ ] 变更日志首条 = 本次会话，`ref` 与 `git log -1` 一致

## 4. 状态口径定义（避免各说各话）

| 状态 | 判定标准 | 允许的例外 |
|---|---|---|
| 🟢 已完成 `done` | 该阶段文件清单全部落地 + 本模块编译 0 error + 全量 `package` SUCCESS + 已 commit + 任务卡执行记录已回写 | 前端阶段以 `npm run build` 通过为准 |
| 🟡 进行中 `doing` | 已开工但存在未提交 / 未编译验证 / 部分文件未落地 / 等待依赖卡 | 用户主动中断也记 doing |
| 🔴 未开始 `todo` | 未派发，或仅完成「卡面修复」（文档层面），代码零改动 | — |

**完成率口径**：任务卡完成率 = `done 卡数 / 17`；会话单元完成率 = `done 阶段数 / 36`。两个数都展示，不互相替代。

## 5. 会话结束检查清单（WorkBuddy 逐项打勾）

1. [ ] Claude Code 是否给出了可解析的 RECEIPT？
2. [ ] `git log --oneline -3` 是否能看到该 commit？工作区是否残留未提交改动？
3. [ ] `mvn -q -DskipTests package` 是否**由本会话真实执行过**（而非引用旧结果）？
4. [ ] 任务卡「执行记录」是否已新增一行？
5. [ ] 回执是否已落 `.workbuddy/receipts/`？
6. [ ] `dashboard_update.py --receipt` 是否执行成功、`--check` 是否通过？
7. [ ] `.workbuddy/memory/今天.md` 是否追加了本次结论与遗留？

> 任一项未完成，不要对用户说「已完成」，应说明卡在哪一步。

## 6. 反例（明确禁止）

| 反例 | 为什么错 |
|---|---|
| Claude Code 直接 `Edit .workbuddy/dashboard/dashboard.html` | 多会话并发会互相覆盖；看板失去可信度 |
| 日志标题写「XX 阶段完成」但回执 `status=doing` | 标题与状态打架，看板会谎报进度。脚本已加保护：非 `done` 状态强制改题并打 `[WARN]` |
| 编译失败但看板标 🟢 | 看板变成"愿望清单"，P0 验收直接踩空 |
| 用「预计完成」「应该能过」填 `maven.result` | 数据不可追溯，违背第 3.5 条第 3 项 |
| 把两个阶段合并成一次派发 | 违反 CLAUDE.md §7「一次只做一个任务卡的一个阶段」，回执与 commit 粒度对不上 |
| 只在 `issues` 写"无"而实际有遗留 | 遗留问题会在下一卡变成返工 |
